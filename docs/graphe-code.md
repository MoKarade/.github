# Graphe de code local (graphifyy) : hooks, wiki et MCP

**Statut : déployé le 21/10/2026 (choix de Marc : runbook complet), tâche MoKarade/.github#336, modèle du pilote app-template (#323).** Le graphe est construit à chaque démarrage de session, sans jeton, et interrogé avant de lire ou grepper des fichiers.

## Ce qui est posé
- `scripts/graphe.sh` : seul point d'entrée (version épinglée `graphifyy[sql,mcp]==0.9.93`, venv dans `~/.cache`, `GRAPHIFY_BACKEND=none`). `update`, `query "<question>"`, `affected "<symbole>"`, `path "A" "B"`, `explain "<symbole>"`, `god-nodes`, `wiki`, `serve`, `session`, `hook-guard`, `garde-lecture`, `usage`.
- `.claude/settings.json` : hook `SessionStart` (rend `graphify` utilisable dans la session via `CLAUDE_ENV_FILE`, puis construit le graphe ET le wiki EN ARRIÈRE-PLAN, sans jamais bloquer ni échouer) ; hooks `PreToolUse` sur `Bash|Grep` et `Read|Glob` (rappel « interroge le graphe d'abord », silencieux tant que le graphe n'existe pas ; échec ouvert) ; en plus, sur `Read|Glob`, `garde-lecture` REFUSE (voir plus bas).
- `.mcp.json` : serveur MCP `graphify` en stdio (`query_graph`, `get_node`, `get_neighbors`, `get_community`, `god_nodes`, `graph_stats`, `shortest_path`, `list_prs`, `get_pr_impact`, `triage_prs`), à approuver à la première ouverture.
- `graphify-out/` (graphe, rapport, wiki, cache) : généré, JAMAIS committé. Le wiki (`graphify-out/wiki/index.md`) sert de plan de navigation.
- Un pointeur d'une ligne dans `README.md` (ce dépôt n'a pas de `CLAUDE.md` ; `AGENTS.md` reste réservé aux consignes de Jules). Pas les 11 lignes de l'installeur officiel.

## Règles (chacune vient d'un constat)
- **0 jeton, 0 clé** : `update` est local (Tree-sitter), sans appel réseau ni LLM ; le paquet ne contacte le réseau que pour `add`, `clone` et les commandes LLM. [Certain, code lu et `strace`]
- **Jamais `label` ni `cluster-only` sans `GRAPHIFY_BACKEND=none`** : sans clé API ils se replient sur `claude -p` et consomment le quota Claude. [Certain]
- **N'utilise PAS l'installeur officiel** (`graphify claude install`, `graphify hook install`, skill `/graphify`) : il réécrit `CLAUDE.md`, pose des hooks vers un chemin absolu et la skill lance des sous-agents LLM. Tout passe par `scripts/graphe.sh`. [Certain]
- **`graphify-out/` jamais versionné** : les commentaires `TODO:`/`NOTE:`/`FIXME:` et les docstrings y sont copiés (80 caractères, e-mails compris) ; `graph.html` charge unpkg. Dépôt public : aucune donnée perso dans un commentaire de code. [Certain]
- **Toujours depuis la racine** : `graphify update /chemin/absolu` écrit ce chemin dans `.graphify_root`. [Certain]
- **Version épinglée** : le paquet sort presque une version par jour ; monter la version = relancer la mesure ci-dessous. Sans l'extra `[sql]`, les migrations `.sql` donnent 0 nœud. [Certain]
- **Les hooks de dépôt ne tirent que si la session démarre DANS le dépôt** (constat du 18/10/2026 : un fil du projet lancé depuis `/home/user` ne charge pas `.claude/settings.json`). [Probable] Dans ce cas il reste `scripts/graphe.sh` à la main.
- **Le rappel injecté dit « MANDATORY »** : c'est le texte du paquet, posé par NOTRE hook ; il coûte ~110 jetons par `Grep`/`Bash` quand le graphe existe.

## Ce que ça apporte, ce que ça n'apporte pas (mesure BatchChef, 21/10/2026, 290 fichiers)
- Le « 61,6x » de `graphify benchmark` compare à la lecture de TOUT le dépôt, ce que personne ne fait. Contre `grep` + lecture du fichier utile, sur 4 questions à symbole connu : 12,3 k jetons contre 12,0 k (requête + extrait), aucun gain net ; la requête ramène des nœuds génériques. [Certain pour ces 4 questions, n = 4]
- Ce que `grep` ne donne pas : `affected "X" --depth 2` rend les importeurs transitifs ET les documents qui citent X, avec fichier:ligne. [Certain]
- Les chiffres du document source (71,5x, -80 %, 76 % LongMemEval) viennent du fournisseur, sur d'autres corpus. [Probable]

## Page visuelle lisible (tâche MoKarade/.github#371, 21/10/2026)
- `graph.html` complet (fait par `graphify update`) est illisible : 25 à 40 % de nœuds de documents, des titres de doc en tête des « god nodes », 1 à 7 k nœuds. Il reste utile pour les requêtes, pas pour regarder.
- `scripts/graphe-page.py GRAPH_JSON SORTIE.html [--max-noeuds 400] [--titre …]` produit une vue par FICHIER : code des dossiers sources seulement (sans tests, générés, dépendances, config, docs, fichiers isolés), un lien = au moins un appel ou import entre deux fichiers, couleur = dossier, panneau sous le graphe sur téléphone. Local, 0 jeton, 0 réseau ; interprète : celui du venv de `graphe.sh` (`~/.cache/graphe-venv-<version>/bin/python`).
- Mesure du 21/10/2026 sur les 9 dépôts clonés (fichiers sur la page / poids du HTML) : app-template 20 (34 Ko), DriveAI 53 (75 Ko), Hubperso 98 (115 Ko), batchchef 135 (142 Ko), MemoryAI 159 (217 Ko), CarAI 170 (199 Ko), JobAI 214 (252 Ko), FinanceAI 400 plafonné (680 Ko ; 623 fichiers reliés avant plafond), hub-contract 2. Avant : 0,2 à 2,6 Mo. [Certain, mesuré]
- Rendu vérifié en Chromium sans tête à 1280 et 390 px (JobAI, CarAI) ; le panneau passe sous le graphe à moins de 700 px. Le moteur `.gs` de DriveAI n'est pas dans cette page (second graphe, `graphe.sh moteur`).
- `graph.html` charge `vis-network` depuis unpkg : une page publiée doit le servir ou l'accepter. Les requêtes (`query`, `affected`) gardent le graphe complet.

## Artefact `graphe` pour Hubperso (tâche MoKarade/.github#374, 21/10/2026)
- Workflow commun `.github/workflows/graphe.yml` (`workflow_call`, entrées `runner` et `depot`) : coche le dépôt appelant, `scripts/graphe.sh update`, `graphe-page.py` de CE dépôt, puis téléverse l'artefact Actions `graphe` (retention 90 jours) à chaque push sur la branche par défaut. L'appel est un job séparé, jamais un check requis ; exemple en tête du fichier.
- Contenu : `graph.html` (page filtrée, moins de 1 Mo, vérifié par le job) et `meta.json` : `{depot, sha, genereLe, noeuds, aretes, filtre}`, `filtre` = `fichiers-v1;max400` (changer `VERSION_FILTRE` quand les règles de tri changent). Aucun commentaire de code, TODO ni contenu : seulement des chemins de fichiers et des dossiers.
- Zéro coût : dépôt privé = robot du PC (`[self-hosted, pc-marc]`), jamais `ubuntu-latest`. `graph.html` charge `vis-network@9.1.6` depuis unpkg ; Hubperso le remplace par sa copie auto-hébergée.
- Appelants (tâche .github#327, 21/10/2026) : chaque dépôt a un `.github/workflows/graphe.yml` (`.github/workflows/graphe-publier.yml` ici) qui appelle le workflow commun à chaque push sur sa branche par défaut. Le script de tri est récupéré APRÈS `graphe.sh update`, pour que ses fichiers n'entrent pas dans le graphe du dépôt appelant. Première preuve : app-template, run 39649987473, artefact de 8 835 octets (20 fichiers, 20 liens).

## Mesure de l'impact : `impact.json` (tâche MoKarade/.github#465, 22/10/2026)
- Le workflow commun ajoute `impact.json` à l'artefact `graphe`, à côté de `meta.json` : `scripts/graphe-impact.py` (stdlib seule, 0 jeton, 0 réseau). Un échec de la mesure ne retire jamais le graphe : la mesure avertit (`::warning::`) et l'artefact part sans `impact.json`. L'historique est la suite des artefacts (un par push, 90 jours).
- Schéma `impact-v1` : `{version, depot, sha, genereLe, methode, taille, banc, totaux}`. `taille` : `noeuds`, `aretes`, `fichiers`, `communautes`, `langages` (extensions les plus fréquentes), `page_noeuds`, `hors_page`, `construction_s`, `cycles_import`, `liens_surprenants`. `banc` : 10 lignes au plus, les symboles de code les plus reliés du graphe (identifiants d'au moins 5 caractères, hors tests et docs) ; par ligne `graphe_caracteres|jetons|ms` (sortie de `scripts/graphe.sh affected`), `grep_caracteres|jetons|ms` (sortie de `git grep -nwI`), `fichiers_graphe`, `fichiers_grep`, `fichiers_communs`, `graphe_en_plus` (dépendants indirects que grep ne donne pas), `grep_en_plus` (fichiers que le graphe manque), `rappel` (communs / fichiers de grep), `grep_commentaires` (lignes de commentaire ramenées par grep), `grep_exclus` (lignes écartées de la baseline car géantes). Au niveau de l'objet : `cycles_exemples`. `totaux` : `lignes_mesurees`, `graphe_jetons`, `grep_jetons`, `economie_jetons` (1 - graphe / grep, négative si le graphe coûte plus), `rappel_moyen`, `graphe_ms_median`, `grep_ms_median`.
- Règles : jetons estimés = caractères / 4 ; fichiers comptés = code hors tests et hors docs ; une valeur non mesurée (appel échoué, délai de 120 s dépassé) vaut `null`, jamais 0 ; `scripts/graphe-impact.test.mjs` valide le schéma et refuse tout autre texte ou nombre négatif (sauf `economie_jetons`).
- À lire avec ses limites : le banc prend les symboles les PLUS reliés (souvent des types), pas des questions choisies ; le rappel est donc plus bas que sur la mesure manuelle du 21/10 (appelants réels de fonctions). `affected` coûte plus de temps que `grep` (environ 1,4 s contre 16 ms sur FinanceAI au 22/10/2026 matin, environ 0,3 s depuis la tâche #490) : le gain est en jetons et en dépendants indirects, pas en vitesse. [Certain, mesuré sur FinanceAI le 22/10/2026]
- Changement de définition le 22/10/2026 (tâche MoKarade/.github#491) : la baseline `git grep -nwI` exclut désormais `dist/`, `build/`, `.next/`, `coverage/`, `node_modules/` et écarte les lignes de plus de 1 000 caractères (code minifié ou généré), comptées dans `grep_exclus` par ligne du banc. Avant, hub-contract (dist/ commité) et Hubperso faussaient la médiane : l'économie de hub-contract passe de 0,995 à 0,42 et son rappel de 0,04 à 0,20 sur la même tête. Les mesures d'avant le 22/10/2026 ne se comparent pas sans cette réserve. Depuis la tâche #490 le banc appelle `affected` à la profondeur 1 (défaut du script).
- Structure du graphe (même tâche) : `taille.cycles_import` (cycles d'import de 5 fichiers au plus, `graphify.analyze.find_import_cycles`), `taille.liens_surprenants` (nombre, plafonné à 200, `surprising_connections`) et `cycles_exemples` (au plus 5 cycles, listes de chemins de fichiers). `null` si la mesure a échoué ; jamais de contenu de fichier. Premier relevé local : FinanceAI a 1 cycle (`services/projection.ts` et `services/projection/strategySearch.ts`).
- L'usage réel (requêtes `affected` / `query` par session) est dans le journal local de `scripts/graphe.sh` (voir plus bas), pas dans `impact.json`.

## Vitesse, profondeur par défaut et journal d'usage (tâche MoKarade/.github#490, 22/10/2026)
- **Délai** : `affected` passe d'environ 1,2 s à environ 0,3 s. `pret()` importait le paquet `mcp` (≈ 850 ms) à CHAQUE appel ; il teste maintenant sa présence par `find_spec` (≈ 20 ms). Le même appel direct de graphify prend ≈ 0,24 s. [Certain, mesuré le 22/10/2026]
- **Profondeur** : `affected` remonte 1 niveau par défaut ; `--depth 2` donne le rayon d'impact complet (importeurs des importeurs). Sur 9 dépôts et 90 symboles (22/10/2026), la sortie est 2 à 3 fois plus courte à la profondeur 1 et le rappel face à grep presque inchangé, mais deux fois moins de fichiers sont cités. Avant une suppression ou un renommage, demander `--depth 2`. [Certain pour la mesure]
- **Journal** : chaque appel `query`, `affected`, `path`, `explain`, `god-nodes` écrit une ligne dans `graphify-out/usage.jsonl` (heure, commande, durée, caractères rendus, branche ; jamais les arguments) et les hooks y comptent leurs passages. `scripts/graphe.sh usage` résume ; un journal vide ou sans ligne valide rend « aucun usage valide » et le code 0 (tâche #503, test `scripts/graphe-usage.test.mjs`). Il mesure l'usage, pas l'économie de jetons : un hook ne voit pas la sortie des outils et deux sessions ne font pas la même tâche. Local, ignoré par git.
- **Lecture ciblée** : `affected`, `explain` et le MCP donnent des `fichier:Lnn`. Lire alors la zone utile (`Read` avec `offset` et `limit`) plutôt que le fichier entier. Le gain en jetons n'est pas mesuré chez nous. [À vérifier]

## Le graphe doit rester en place : contrôle de conformité (tâche MoKarade/.github#841, 29/10/2026)
- `scripts/graphe-en-place.mjs` (fonction pure `controlerGrapheEnPlace`, aucun réseau ni jeton) est exécuté par le workflow commun `conformite.yml` sur le dépôt appelant, dans l'étape « Graphe de code en place ». Il nomme chaque manque : `scripts/graphe.sh` absent ou de moins de 2 Ko ; `.claude/settings.json` absent, illisible ou sans hook `SessionStart` ou `PreToolUse` vers `scripts/graphe.sh` ; `.mcp.json` absent, illisible ou sans serveur `graphify` qui lance `scripts/graphe.sh serve`. Un JSON invalide compte comme un manque, jamais comme une exception.

- Ce que le contrôle ne vérifie pas encore : le hook `garde-lecture` (#840) et l'identité de la copie de `graphe.sh` entre dépôts. Il le fera quand les 9 autres dépôts auront reçu la copie à jour. [Certain : les 10 clones locaux passent le contrôle actuel le 29/10/2026]

## Lecture massive refusée par le hook (tâche MoKarade/.github#840, 29/10/2026, demande de Marc : une obligation mécanique, pas une consigne)
- `scripts/graphe.sh garde-lecture` lit le JSON du hook `PreToolUse` sur l'entrée standard et rend une décision `deny` dans deux cas seulement : un `Read` SANS `offset`, `limit` ni `pages` d'un fichier de plus de 400 lignes ou 40 Ko (hors `.md`, `.txt`, images, PDF, `*.lock`, `package-lock.json`, `*.min.js`), et un `Glob` de tout le dépôt (`**`, `**/*`, `**/*.*` sans dossier). Le motif du refus cite la commande du graphe à utiliser (`explain`, `affected`, `query`) puis `Read` avec `offset` et `limit`.
- Échec ouvert : JSON illisible, fichier absent ou hors du dépôt, autre outil, python absent → silence, code 0. Le hook ne dépend pas du graphe (il refuse même graphe absent). Chaque refus écrit `garde-lecture-refus` dans `graphify-out/usage.jsonl`.
- Contournement honnête : relire avec `offset` et `limit` (la zone utile), jamais en désactivant le hook. Les seuils (400 lignes, 40 Ko) sont en tête du script, à ajuster d'après les refus journalisés. [Probable : seuils choisis sans mesure]
- Test : `scripts/graphe-garde-lecture.test.mjs` (workflow `tests-graphe-page.yml`). Le hook ne se charge que dans une session ouverte DANS le dépôt (limite connue de `.claude/settings.json`).

## Commentaire d'impact sur chaque PR (tâche MoKarade/.github#842, 29/10/2026, demande de Marc : le graphe doit servir sans que personne y pense)
- Le workflow commun `impact-pr.yml` (appelé par chaque dépôt sur `pull_request`, job séparé, jamais un check requis) construit le graphe de la tête de la PR, lance `scripts/graphe.sh affected <fichier> --depth 2` pour chaque fichier de CODE modifié (12 au plus, tests en dernier) et pose UN commentaire mis à jour sur place (marqueur `<!-- impact-graphe -->`) : par fichier, le nombre de fichiers qui en dépendent, dont les tests, et les 8 premiers. Rien à dire (aucun fichier de code, aucun dépendant) = aucun commentaire, et l'ancien est retiré.
- Garde-fous : ignoré pour une PR de fork (jeton en lecture seule) et pour les robots (Dependabot, Mergify) ; aucun jeton de LLM ; le jeton GitHub n'est donné qu'à la dernière étape ; le script (`scripts/impact-pr.mjs`) vient de ce dépôt, jamais de l'appelant ; les chemins sont des données, écrits dans un segment de code sans retour à la ligne ni accent grave ; chaque étape se rattrape par un avertissement (jamais de rouge ajouté).
- Dépôt public = `ubuntu-latest`, privé = robot du PC. Appel : voir l'en-tête de `.github/workflows/impact-pr.yml` ; pour .github lui-même, `.github/workflows/impact.yml`. Test : `scripts/impact-pr.test.mjs`.
- Limite : `affected` suit les imports et appels statiques ; un appel dynamique peut manquer (rappel mesuré à 71 % en médiane, 22/10/2026). Le commentaire est un point de départ, pas une preuve d'absence d'impact. [Certain pour la mesure ; l'usefulness du commentaire sur de vraies PR reste à observer]
